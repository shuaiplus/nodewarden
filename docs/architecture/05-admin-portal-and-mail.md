# Admin portal and mail

Transactional email uses Cloudflare's `EMAIL` binding through `sendMail` and data-only templates. Every message has text and escaped HTML, one recipient, and `Auto-Submitted: auto-generated`. User-supplied names are stripped of control characters, addresses and link schemes before rendering. Subjects never include tokens. Documentation domains are skipped.

`EMAIL` absent disables delivery. With the binding present, an invalid sender or sender name is a configuration error. Authenticated invitation flows await delivery before saving; disabled mail preserves local invite behavior, invalid config gives 503 and failed delivery gives 502. Error responses and logs omit recipient addresses and tokens.

Set `EMAIL_FROM` to an address on an onboarded sending domain and optionally set `EMAIL_FROM_NAME` (default `NodeWarden`). Use a sending subdomain. Arbitrary recipients require Workers Paid; verified Email Routing destinations can be used on Free. Development uses the local simulator, without `remote = true`.

Vault links use configured `WEB_VAULT_ORIGINS`. They never follow `X-Forwarded-Host`. Delivery code is independent of the background task adapter, which attaches notices to Workers `waitUntil`.

Cloudflare API references: [Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/), [local email simulation](https://developers.cloudflare.com/email-service/local-development/sending/).

## Administrator access

`ADMIN_EMAILS` enables `/admin` on the Worker origin and defines full administrators independently of vault accounts. Each comma-separated entry is `email` or `email:stamp`. Removing an address or rotating its stamp immediately invalidates links and sessions. Unset configuration hides the portal; malformed entries give a generic portal error without disabling the vault.

Sign-in links use 32 random bytes, stored hashed in `verification`, and expire in 15 minutes. GET only renders a button. POST consumes the row atomically, requires the requesting browser's secure HttpOnly nonce cookie, and creates a fixed two-day revocable session. Resends retain a valid browser nonce so a suppressed or failed send does not invalidate earlier delivered links. Links cannot be opened on another device. Worker request logs can contain the GET token, so disable Email preview and protect logs; the token alone is insufficient without its browser cookie.

All portal responses disable caching and CORS. Form POSTs require the exact Worker origin (or same-origin Fetch Metadata when Origin is absent); authenticated forms also need a session-derived CSRF token. Requests with Fetch Metadata must be document navigations, preventing other same-origin scripts from reading forms. Logout deletes the server session. Login requests are capped per IP; link delivery is separately capped per administrator without revealing that budget or directory membership in the response.

The dashboard shows account/organization/admin counts, compatibility version, mail/SSO/push/Yubico configuration status, registration and vault-origin settings, and the last 20 portal audit events. It never renders credentials or the configured admin directory and makes no outbound requests.

Users can be searched by literal email prefix and paged at up to 100 rows. Details expose account metadata, factor status and counts only; personal item counts exclude organization items. Deletion requires CSRF, a sign-in within 15 minutes and typing the user's email. A shared service refuses sole owners, accounts with organization items that cannot be reassigned, and the last active vault administrator. Organization items are handed to another confirmed member and retain their blobs; personal blobs are removed only after the atomic deletion and audit batch commits. Administrator invite codes cascade on deletion. Sensitive portal actions share a cap of 20 per administrator per hour.

Organization pages filter names with literal contains matching and members by either invited or account email. Details show metadata, member states, administrators and resource counts, including active Secrets Manager secrets; encrypted names and key material never render. Deletion requires a fresh sign-in, CSRF and the exact organization name. The shared deletion batch removes organization data and bumps members' revisions before cleaning blobs; its audit row commits atomically.

Registration verification checks delivery configuration before account lookup: disabled or invalid mail gives 503 for every address. Otherwise all valid addresses get an empty JSON string immediately; existing and reserved accounts send nothing and new accounts are mailed in the background. Links select a configured vault origin, falling back only to the Worker request origin. Delivery failures never change the public response.

User-triggered templates spend strict D1 budgets before sending: `EMAIL_SENDS_PER_HOUR` per instance (default 100), and five messages per recipient per hour. Failures are not refunded. Authenticated flows return 429 with Retry-After before saving; anonymous flows keep their uniform response and log suppression in the background. Administrator links and security notices are exempt. Keep the hourly instance limit × 24 below the account's daily quota.

Successful password (including SSO), passkey and API-key logins notify existing accounts when a previously unseen device is persisted. Accounts younger than ten minutes and documentation addresses are skipped. Notices include the device type, UTC time and IP, and never delay login. `DISABLE_EMAIL_NEW_DEVICE` accepts `0`, `1`, `true`, or `false`; malformed values make mail misconfigured and log the configuration field. The addendum's independent `ENABLE_NEW_DEVICE_VERIFICATION` flag is handled separately and does not make mail misconfigured.

A failed two-step check after a valid password sends at most one security notice per account per hour. Remember-device failures do not mail; incorrect recovery codes identify the recovery-code provider. The D1 dedupe budget is claimed before background delivery, so a failed delivery also suppresses repeats for that hour. Notices are exempt from user-triggered mail budgets and never alter the login response.

Successful recovery through the recovery endpoint or recovery-code login sends a security notice after factors and sessions are cleared. Wrong recovery codes after a verified password use the failed-two-factor notification budget. Delivery failure never reverses a successful recovery.

With email enabled, password-hint requests always return `sentByEmail: true` and no hint, regardless of account existence or status. Active accounts receive either their sanitized hint or a no-hint notice in the background, subject to mail budgets. Misconfigured mail gives 503 uniformly. Disabled mail retains the legacy inline hint response; administrators should treat that fallback as an intentional information-disclosure risk.
With mail and a configured vault origin, emergency-access invites require a dedicated, five-day token even for existing accounts. Delivery must succeed before saving, and each grantor can send ten invites or reinvites per hour. Without mail or a vault origin, existing-user invitations still auto-accept. After enabling mail, reinvite pending contacts to supply their required token. New-account invitees need open registration; an emergency-access invitation does not grant registration permission.

Successful account creation sends one background welcome mail, including the first instance administrator, invite-code signups and open registration. Failed registrations send none. Delivery failure does not undo account creation; the vault link is omitted when no vault origin is configured.

User details provide disable/enable forms protected by CSRF. Disabling rotates the account security stamp, revokes sessions and pushes logout, so enabling never revives old tokens. Vault data, Sends, emergency access, memberships and devices stay in place. The last active vault administrator cannot be disabled; portable backup settings are re-wrapped for the remaining active administrators.

Better Auth sessions are authoritative in D1; KV is used only for its rate-limit counters. It also refuses session creation for disabled accounts, so `/api/auth` cannot restore a session after disable. An access token already cached in another Worker isolate can remain usable for the existing cache lifetime of up to 15 seconds.

Vault roles follow `ADMIN_EMAILS` after startup, registration, email verification, account enablement and backup restore. Sync requires at least one listed, verified, active account; otherwise it preserves existing roles. New registrations record verification only after a matching emailed token, while old accounts and legacy archives retain their verified default. Profile and JWT verification flags stay compatible with official clients. Generic user saves cannot undo derived roles or verification. Role changes re-wrap decryptable backup settings for the current active administrators; portable-only restored settings still use the existing repair flow.

An unverified account can be marked verified from its details page after signing in within 15 minutes, supplying CSRF and typing the account email. For a listed address, the button explicitly says it also grants vault administrator access. Verification and deletion share the sensitive-action budget; each verification is audited.

The user view names enabled two-step providers. Removing two-step login requires fresh sign-in, CSRF and a typed email, and shares the sensitive-action budget. One batch clears two-step credentials, the recovery code, Better Auth secret, remembered-device tokens and sessions, rotates the security stamp and writes the audit event. Login passkeys remain. The account receives a background notice stating an administrator removed two-step login, without an IP address or administrator identity. A user with no enabled factor produces no reset, audit or notice.

Ordinary factor removal preserves existing Remember-device trust, matching upstream. Recovery and administrator resets deliberately revoke that trust as well as sessions.

Email can be enrolled as a two-step provider through the official settings API. Setup requires a provider-bound verification token or fresh master-password verification and a code sent to the normalized factor address. Enrollment creates a recovery code if needed. GET settings and factor removal work even when mail is unavailable; the factor never disables itself on delivery failure.

All email codes use `email-otp.ts`: six unbiased random digits, a five-minute lifetime, purpose/subject/binding-separated HMAC identifiers and values, single-use redemption, and five attempts per lifetime. Setup/change/Send issuance permits five per subject per hour; sign-in codes have a separate twenty-per-hour allowance. The cron removes expired OTP rows. A failed or throttled resend keeps the preceding delivered code. No plaintext code enters storage or a subject line.

Account creation is INSERT-only and profile saves are UPDATE-only with an explicit field list. Password/key, API-key and factor writers name their intended columns and reject writes whose original security stamp no longer matches; stale profile requests cannot roll credentials back or recreate a deleted account. Recovery codes use targeted atomic creation/reset writes.

Email two-step login sends a code only after a valid master-password proof, approved device auth request, or five-minute account-bound send-email session token. Present credentials are exclusive in that order: access code, then session token, then password; a bad token never falls through. The challenge masks the factor address and includes the account address and send token for official clients. The send token cannot authenticate a login. Codes go to the factor address, remain stamp-bound and single-use, and failures use the ordinary two-factor lockout and notice path.

`ENABLE_NEW_DEVICE_VERIFICATION` accepts `0`, `1`, `true` or `false` and defaults off. It runs only with configured mail, on password-only logins for opted-in accounts at least one day old with existing device history. Unknown or missing device identifiers trigger a background sign-in code without creating a device row. A supplied code is validated before known-device/empty-history exemptions, so a replay fails even after the first success creates its device. Codes have no device binding. Success records real email verification. OTP failures use the code attempt budget without spending the password lockout budget. SSO, approved device requests, two-factor, API-key and passkey grants are exempt.

New accounts opt into the stored preference, and a marker-guarded migration backfills old accounts once. Backup import preserves the marker so a later schema replay cannot undo restored opt-outs. The account preference requires a verified master password; the obsolete two-factor device-settings routes remain disabled compatibility responses. Anonymous resend keeps unknown accounts and wrong passwords indistinguishable. A malformed optional NDV flag logs an error and disables this check while mail and Email two-step login remain enabled.

Anonymous account-deletion recovery requests return the same empty success for known, unknown and disabled addresses; only active accounts receive mail. Mail and a configured vault origin are required uniformly. Requests are limited to five per IP per hour. The one-day token is bound to the user and security stamp and stays in the link fragment. Redemption rejects unknown/disabled accounts, bad or expired tokens and changed stamps with one error; it reuses the guarded deletion service and consumes the token by deleting the account. Self and recovery deletion also check the original stamp inside the deletion batch, so a mid-flight password change cancels deletion. Portal deletion keeps its independent administrator authorization.

Email change first verifies the current master-password hash against the old email. A taken address sends an informational notice to the current address; a free address receives a six-digit code. Both branches return the same empty success and spend the same five-per-user/hour issue budget once. The code binds the current stamp and normalized destination address. Invalid key or KDF input is rejected before consuming it.

The final email/hash/key update, credential account upsert, session deletion, revision and audit are one stamp-guarded D1 batch. Unique-email races and audit failures roll back all account changes. Restored accounts without a credential row get one in that batch. Old access/refresh tokens stop working, the old address receives an exempt UTC/IP notice, and vault roles are synchronized. Ordinary password and emergency-takeover credential mirrors also require the canonical current hash/stamp, so delayed writes cannot undo an email change. Better Auth email change remains disabled to preserve the email-salt/key coupling.
