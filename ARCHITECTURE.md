## Runtime

- Worker: `src/index.ts` → `src/router.ts`
- Data: D1 via Drizzle v1 (`src/db/`, `src/services/storage*.ts`, `migrations/`)
- Auth engine: Better Auth (`src/auth.ts`) behind Bitwarden `/identity` and `/api` adapters
- Blobs: R2 or KV (`src/services/blob-store.ts`)
- Push: `NotificationsHub` Durable Object
- Backups: `BackupTransferRunner` Durable Object
- Web vaults:
  - Local: `webapp/` (Preact + Vite) → Worker assets (`dist/`)
  - Official: `official-web/` (Bitwarden OSS self-host Angular) → Cloudflare Pages, API proxied to the Worker

## Data

Schema lives in `src/db/schema.ts` and `src/db/relations.ts` (relations v2). `npm run db:generate` emits nested `migrations/<id>/migration.sql` and embeds SQL into `src/db/baseline.ts` for Worker bootstrap. Bump `STORAGE_SCHEMA_VERSION` when the schema changes. Data-only fixes are `drizzle-kit generate --custom` migrations and bump it too; each bump replays every migration, so every statement must be safe to rerun forever.

Use `db.batch()` for multi-statement work. `db.transaction()` is broken on D1. D1 caps one statement at 100 bound parameters.

Personal vault lists and mutations filter `organization_id IS NULL`. Organization ciphers are loaded by id, then membership and collection ACL in `src/handlers/cipher-access.ts`.

A cipher changes owner only through share (`PUT /api/ciphers/{id}/share`, bulk `PUT /api/ciphers/share`, plus POST aliases). `PUT /api/ciphers/{id}` keeps the stored `organizationId` and returns 400 "Organization mismatch" when the client sends a different one. Share moves only the caller's personal ciphers, at most `importItemLimit` per bulk call. Share and org cipher create (`POST /api/ciphers`, `/api/ciphers/create`) both need every collection to belong to the target org and be writable by the caller, otherwise 400 (not 403, which official clients treat as a revoked token and log out). Only full collection access may create an org cipher in no collection. Upstream drops unwritable ids silently instead. The ciphers, their collection links and their re-encrypted attachment keys are written in one D1 batch.

An org cipher's collections change through `PUT /api/ciphers/{id}/collections_v2` (member) or `/collections-admin` (Owner, Admin or `editAnyCollection`), plus POST aliases. Both add and drop only collections the caller may write: a member's non-readOnly assignments, or every org collection with full access or on the admin route. Links to other collections survive, as in upstream `CollectionCipher_UpdateCollections` and 1aed7ce03. The member route answers `optionalCipherDetails` with `unavailable: true` once the caller can no longer read the item.

Instance backups never include runtime auth state (`session`, `account`, `two_factor`, devices, auth requests, remembered 2FA tokens).

## Auth

Better Auth owns credential hashing (`$s2$` via `src/services/auth-password.ts`), the `session` / `account` / `two_factor` tables, and `/api/auth/*`. Official clients stay on Bitwarden `/identity` and `/api`; those handlers call Better Auth internally where useful and still mint HS256 access JWTs with `JWT_SECRET`. Refresh tokens are rows in `session`, not a separate table.

Official-web signup emails go through the Cloudflare Email Sending binding (`env.EMAIL.send()`). `EMAIL_FROM` must be on an onboarded sending domain. The Worker returns an empty JSON string from `send-verification-email` (never the JWT). Official self-host web still continues to the password form; the email link uses `/redirect-connector.html#finish-signup`. RFC documentation addresses such as `@example.com` get the same empty response without a send.

`better-auth-cloudflare` `withCloudflare()` is not used: its bundled drizzle types clash with 1.0-rc. `src/auth.ts` wires `drizzleAdapter`, KV secondary storage, and `cf-connecting-ip` directly. Worker `nodejs_compat` is required.

## Organization invites

Members move Invited (0) → Accepted (1) → Confirmed (2), as upstream. Invite, and SCIM for an existing account, stores an Invited row with no user and mails its accept link; SCIM answers 409 for an address or `externalId` already in the org, as upstream. Only the invitee can accept it, with the emailed `ORG_INVITE_TTL_DAYS` token, and only Accepted rows can be confirmed. Before confirming, clients read the member's RSA public key from `GET /api/users/{id}/public-key` (any logged-in caller, also used for emergency access) or, in bulk, `POST /api/organizations/{orgId}/users/public-keys` (member managers; Accepted members of that org only). Confirm requires the key to carry an RSA EncString type (3-6): the org key wrapped with that public key, as official clients and the Worker webapp (`encryptBwRsa`) send it. Anything else, such as the admin's own symmetric key, is 400, since the member could never decrypt it; upstream only requires a non-empty key. Official web's bulk confirm posts `{keys: [{id, key}]}` to `POST /api/organizations/{orgId}/users/confirm`: each entry gets the same checks and its own `{id, error}` result (`error` is `''` on success; object `OrganizationBulkConfirmResponseModel`, as upstream), and the confirmed rows are saved in one batch. `POST …/users/{id}/reinvite` and bulk `POST …/users/reinvite` (`{ids}`) mail an Invited row a fresh token, the only way back from an expired one; any other row, another org's included, is "User invalid." (400, or per id in bulk). Unlike upstream, bulk results also list missing ids instead of dropping them, so another org's members read like ids that do not exist. Any confirmed member can list every member's id, user id, role, status, name and email from `GET /api/organizations/{orgId}/users/mini-details`, as upstream, which official web's collection and group dialogs need; it carries no keys, permissions or 2FA state. Invite takes 1 to 20 valid addresses per request and skips repeats and addresses already in the org by invited or account email (200 even if none remain), as upstream. Invite mail needs `EMAIL`, `EMAIL_FROM` and `WEB_VAULT_ORIGINS`; the link never follows `X-Forwarded-Host`, the org name in the subject and body is defused with `sanitizeForEmail`, and RFC documentation addresses are skipped. Each inviter may mail `LIMITS.rateLimit.orgInviteEmailsPerHour` invites and resends per hour across all of their orgs (a SCIM directory spends its org's own budget); upstream throttles the invite endpoint per IP instead. Mail goes out before the row is saved, so a failed send (502) or a batch over the budget (429 with `Retry-After`) leaves no row for a retry to duplicate; upstream deletes the rows instead. Without mail, invites cannot be accepted yet. Upgrading from earlier builds: they auto-Accepted existing accounts without consent, so review Accepted (status 1) members and delete and re-invite any you did not expect. They also stored a posted `type` and `accessAll` with no role check, so review Owners you did not appoint, and members other than Owners and Admins that `GET /api/organizations/{orgId}/users` lists with `accessAll` set; they keep full collection access until edited.

An Invited row has no user for `collection_users`, so its direct collection access waits in `pending_collection_users`, keyed by membership. Invite writes all memberships with their access and groups in one D1 batch. Accept binds the user and moves the pending access with an `INSERT ... SELECT` in the same batch (`saveAcceptedMembership`), so a collection save between a read and the write is never lost.

Single and bulk remove, revoke and restore share the role, self-action and already-active/revoked checks. Bulk `PUT/PATCH …/users/revoke` and `…/users/restore`, `DELETE …/users`, and `POST …/users/remove` accept `{ids}` and report an empty error string per success; missing and foreign members both return `Invalid user.` per id. Accepted changes use one chunked D1 batch. Membership deletion, including leave and SCIM, updates revisions before deleting rows, so the removed user's cached sync is invalidated too.

Invite and PUT run `memberRoleChangeCheck` (`src/services/org-authz.ts`), upstream `CanManageRoleChange`: the caller must manage both the member's current and requested type, else 400. Owners manage anyone, Admins anyone but Owners, Custom `manageUsers` members only Users and Custom members, granting only permissions they hold. PUT answers 400 if the change would leave no confirmed Owner, as upstream. `DELETE /api/organizations/{orgId}/users/{id}`, `PUT …/users/{id}/revoke` and `…/restore` apply the same type rule to the member's current type (`memberRemovalCheck`) with upstream's per-action 400, such as "Only owners can remove other owners." or "Custom users can not revoke admins.". Remove and revoke also refuse the last confirmed Owner with PUT's 400 (upstream `HasConfirmedOwnersExceptAsync`), since only an Owner could restore it; an Invited, Accepted or revoked Owner never counts. Invite and PUT store `accessAll` as false, which upstream's requests lack, so new and edited rows get full collection access only from the Owner or Admin type.

Invite and `PUT /api/organizations/{orgId}/users/{id}` grant direct collection access only where the caller may modify it: Owners, Admins and `editAnyCollection` members anywhere, anyone else only on collections it holds with the stored Manage flag, directly or via a group ("Can edit" does not count). Anything else is 404 "Resource not found.", except an entry that repeats the member's current access unchanged, because official web offers every collection it shows. PUT keeps the member's access to collections the caller cannot modify, whether re-posted or omitted. A member without full collection access editing itself gets 400 "You cannot add yourself to a collection." for a new collection, and its posted groups are ignored. `memberCollectionsCheck` is upstream `GetAuthorizedCollectionsToSaveAsync` with `allowAdminAccessToAllCollectionItems` off, applied to everyone but Owners and Admins, although `org-response.ts` advertises that setting as on; with it on, upstream lets `manageUsers` alone grant any collection. Group membership on invite or PUT stays unchecked, as upstream.

## Organization collections

Official web's collection dialog opens from `GET /api/organizations/{orgId}/collections/details` and saves the full member and group lists back, so every collection response carries upstream `CollectionAccessDetailsResponseModel` grants: `users` by membership id (bound members from `collection_users`, invited ones from `pending_collection_users`) and `groups` from `collection_groups`. `/collections/{id}/details` is the single object `bw get org-collection` reads, `/collections/{id}/users` the bare member array, and create and update answer with the saved collection's details. Readers and updaters follow upstream's authorization handlers (`canActOnCollection`): Owners, Admins and `editAnyCollection`, `deleteAnyCollection` or `manageUsers` members read any collection's access (`manageGroups` also lists them all, `/users` drops `manageUsers`), and only Owners, Admins and `editAnyCollection` members update any collection. Anyone else reads or updates only collections it holds with the stored Manage flag ("Can edit" does not count), so `/collections/details` lists only those (NodeWarden's webapp lists names from `/collections`); others get 404, and create or update answers a caller who may not read access with no grants. `assigned` and the caller's flags follow `resolveCollectionPermission`, since sync gives Owners and Admins every collection; its `manage`, also in sync and `/collections`, is the stored grant alone for everyone else, as upstream, so clients never offer an update the server refuses; a reader holding no grant gets every flag false. On create or update an omitted `users` or `groups` list leaves that access as is and an empty one removes it, as upstream `ReplaceAsync`. `replaceCollectionAccess` writes both lists in one batch with chunked inserts, so a large save cannot delete the old grants and then fail.

## Secrets Manager

Legacy raw-bearer sync (`GET /api/organizations/{org}/secrets/sync`) returns only secrets in projects the machine account has a read grant on. Accounts created by the old webapp token button have no grants and sync nothing. Until access-policy routes are available, create a replacement with `POST /api/organizations/{orgId}/service-accounts` (`{name, projectIds}`), create its token with `POST /api/service-accounts/{id}/access-tokens` (`{name}`), and replace the operator's authentication secret; names must be encrypted under the organization key.

Secrets Manager is on for every organization and never reads a license. Organization and profile responses always send `useSecretsManager: true`, license upload (`POST /api/organizations/licenses/self-hosted[/{orgId}]`) ignores every Secrets Manager field such as `useSecretsManager`, `smSeats` and `smServiceAccounts`, and there are no seat, project or machine-account limits. Confirmed Owners and Admins get `accessSecretsManager` in the profile, member list and member detail through `canAccessSecretsManager`, the same gate the Secrets Manager API checks. `scripts/sm-license.test.ts` pins this.

The server never holds an organization key. Access token creation ignores a posted `wrappedOrgKey`, the machine token (`/identity/connect/token`, `scope=api.secrets`) and sync responses carry none, and the `sm-scrub-org-key` migration clears `sm_access_tokens.wrapped_org_key`. Upgrading from earlier builds: the webapp's access token button posted the plaintext org key there, and both responses returned it. Before deploying, run `npx wrangler d1 execute DB --remote --command "SELECT sa.org_id, COUNT(*) FROM sm_access_tokens t JOIN sm_service_accounts sa ON sa.id = t.service_account_id WHERE t.wrapped_org_key IS NOT NULL GROUP BY sa.org_id;"` (or paste the SELECT into the D1 console of the Cloudflare dashboard) and record only the org ids and counts, never the values. The first request after deploying runs the scrub, and the query then returns nothing, so if you already deployed, treat every organization that had an access token before the upgrade as listed. Each listed organization must treat its org key as disclosed to anyone with D1 or Time Travel access and to every holder of one of its machine credentials. Clients cannot rotate an org key, so move its vault items to a new organization. The old values stay in D1 Time Travel until its retention window passes.

Clients encrypt Secrets Manager names and secret keys, values and notes under the org key, as upstream requires, and the Worker webapp's Secrets Manager page does too. Upgrading from earlier builds: the webapp stored project names in plaintext and created secrets with no note, and its access token button named the machine account and token in plaintext, so official web and bws cannot decrypt them. The server cannot fix these rows; rename or re-save them in official web. Find them with `SELECT id FROM sm_projects WHERE name NOT GLOB '[0-9].*|*'` (likewise `sm_service_accounts` and `sm_access_tokens`) and `SELECT COUNT(*) FROM sm_secrets WHERE note IS NULL`.

Project links never cross organizations. Creating or updating a secret, and creating a machine account with legacy `projectIds`, answers 404 "Resource not found." before any write when a project id is missing, repeated, or belongs to another organization, as upstream `ProjectsAreInOrganization` (`projectsInOrg` checks the ids in chunks). Secret responses, lists and machine sync read a link only when its project is in the secret's organization, scoped by org or secret id rather than an id list, so orgs with more than 100 secrets list and sync. The `sm-same-org-links` migration deletes stored cross-org secret links, and machine-account project grants that cross organizations or lack read access (upstream ignores a grant without read). Saving a secret with its links, and replacing a machine account's project grants, each run as one batch with chunked inserts, so link counts above one INSERT's parameter cap fit and a failed write keeps the previous links.

Secrets Manager project authorization uses `sm-authz.ts` with org-bound member and group grants. Owners and admins can write every project; other confirmed members see only granted projects. Creating a project grants its creator write access.

Secrets Manager people policies grant confirmed members access directly or through organization groups. A member allowed to manage groups can add themselves to a group and inherit its grants. Write access to a machine account permits issuing tokens for everything that account can read. Removing a member does not invalidate tokens they issued; revoke those machine-account tokens separately.

Machine JWTs are separate principals, accepted only by the project/secret CRUD and sync route allowlist. Each request joins the access token to its machine account, so token revocation or account deletion invalidates existing JWTs immediately.
